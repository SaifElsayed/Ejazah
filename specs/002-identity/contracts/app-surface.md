# Contract: The user surface

Every procedure below is mounted on `appRouter`. Kind, input, output, rate
limit and the requirement it serves. A public procedure declares its rate
limit; the user kinds declare their standing (`admits`) and whether a
restricted account may call them. "user" is the new `userProcedure` kind:
any authenticated person of either role, for what both roles share
(contracts/kernel.md).

The email sign-up path: `verifySignUpCode` returns a token whose identity is
the verified email; the password chosen on `EmailSignUp` is held on the device and sent with
`complete` as `password`, the optional input above, required exactly

## What every procedure of this surface guarantees

- Its output schema names every field a client may see; the leak test asserts
  that none names `dateOfBirth` of another person, a storage key, a hash, a
  provider subject or a recipient reference (FR-138).
- No input names `gender`, `role`, `userId` (T159) and none names a timestamp (R-TIME-6); `onboarding.complete` is the one exception the rule admits by design, for exactly two fields, `gender` and `role` — the declarations themselves, made once by the person before any account exists — and the lint rule's allow-list is per procedure and field, holding that one procedure with those two fields and nothing else (R-GENDER-6's test asserts it).
- Every mutation a client may retry whose output carries no token (`teacher.application.submit`, `account.delete`, `teacher.payout.register`) takes the kernel's idempotency key, now per actor (FR-106). A procedure whose output carries a token (`onboarding.complete`, `auth.refresh`, `auth.email.resetPassword`, `auth.email.signIn`, `auth.signInWithProvider`) is never keyed through the table, because the table stores the first outcome in plain JSON (R-DB-7, the Critical of PR #74's review); `complete`'s single use is the `jti` mark, and a lost answer is recovered by signing in again, which now finds the identity.

## Rate-limit subjects

Every public procedure declares `subjectOf` (T170); the subject is what the per-subject limit counts, and the budget caps the path for everyone.

| Procedure                                                                                        | Key                                                                    | Subject                                                                                                             |
| ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `auth.providerNonce`                                                                             | `rate_limit_provider_nonce`, budget `rate_limit_authentication_budget` | the client address (`ctx.clientAddress`, kernel.md)                                                                 |
| `auth.signInWithProvider`                                                                        | `rate_limit_authentication`, budget                                    | the nonce (one per mint, so the per-subject limit is bounded by `providerNonce`'s; the budget holds the path)       |
| `auth.email.requestSignUpCode`, `auth.email.requestPasswordReset`, `onboarding.requestEmailCode` | `rate_limit_one_time_code`, budget                                     | the destination address, lower-cased                                                                                |
| `auth.email.verifySignUpCode`                                                                    | `rate_limit_one_time_code`                                             | the destination address                                                                                             |
| `auth.email.signIn`, `auth.email.resetPassword`                                                  | `rate_limit_authentication`, budget                                    | the email, lower-cased (a password spray per account is counted; the budget stops the spread)                       |
| `auth.refresh`                                                                                   | `rate_limit_token_refresh`                                             | the SHA-256 of the refresh token (never the client address: one carrier NAT must not throttle every user behind it) |
| `onboarding.complete`                                                                            | `rate_limit_authentication`                                            | the SHA-256 of the onboarding token (no parse in `subjectOf`)                                                       |
| `platform.publicConfig`, `catalog.subjects.list`                                                 | `rate_limit_public_page`                                               | the client address (`ctx.clientAddress`)                                                                            |
| `account.delete` (user kind)                                                                     | `rate_limit_authentication`                                            | the caller's user id                                                                                                |
