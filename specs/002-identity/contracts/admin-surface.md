# Contract: The administrator surface

Every procedure below is mounted on `adminRouter`. The sign-in procedures are
on the new `adminPublicProcedure` kind (kernel.md); everything else is
`adminProcedure`, which runs in one transaction and writes the audit record
the handler describes, with the non-personal `targetLabel` rendered by the
writer from the target's type and id (FR-180). A read is audited like a write:
its action ends in `.read` (`applications.read`, `audit.read`, `home.read`,
`admins.read`), a read with no single target names the reading administrator
(`targetType: 'admin'`), and the home's latest actions and `audit.list` leave out
the actions ending in `.read` and nothing else (owner's decision 2026-10-21, T065).

## `auth` — sign-in and the second factor (FR-170 to FR-174)

| Procedure                | Kind                                                  | Input                            | Output                                                              | Notes                                                                                                                                                                                                          |
| ------------------------ | ----------------------------------------------------- | -------------------------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `auth.signIn`            | admin public, `rate_limit_admin_authentication` with budget `rate_limit_admin_authentication_budget` (T133) | `{ email, password }`            | `{ next: 'mfa' \| 'setup', sessionToken }`                          | `ADMIN_SIGN_IN_FAILED` for an unknown email, a wrong password, a disabled account, an unset password or a locked account — one message, one timing (R-107). The token is a session with `mfa_verified_at` null |
| `auth.mfa.verify`        | admin public, `rate_limit_admin_authentication`             | `{ sessionToken, code }`         | `void`                                                              | Marks the session verified; a wrong code counts toward the lockout; a code already accepted in its time step is refused (RFC 6238 §5.2, `admin_users.mfa_last_accepted_step`)                                  |
| `auth.mfa.recover`       | admin public, `rate_limit_admin_authentication`             | `{ sessionToken, recoveryCode }` | `{ remainingCodes }`                                                | Consumes one code and marks the session verified; a wrong code counts toward the lockout                                                                                                                       |
| `auth.mfa.setup.begin`   | admin public, `rate_limit_admin_authentication`             | `{ sessionToken }`               | `{ otpauthUri, manualKey }`                                         | Only while `mfa_enrolled_at` is null; a fresh secret is drawn and written to the row on every begin, valid for that sign-in only (FR-171; owner's decision 2026-10-21, T066). The URI is `otpauth://totp/Ijazah:<email>?secret=<manualKey>&issuer=Ijazah` (otplib's `generateURI`: the label is the issuer, a colon and the administrator's email, percent-encoded; digits and period are the defaults, 6 and 30, and left out); the panel reads the email from the label for the setup page's lede (B14a, owner's decision 2026-10-22), and `totp.spec.ts` pins the shape                                                                                                                                                  |
| `auth.mfa.setup.confirm` | admin public, `rate_limit_admin_authentication`             | `{ sessionToken, code }`         | `{ recoveryCodes: string[] }` (`admin_recovery_code_count` of them) | Sets `mfa_enrolled_at`, issues the codes once, marks the session verified                                                                                                                                      |
| `auth.setPassword`       | admin public, `rate_limit_admin_authentication`             | `{ inviteToken, password }`      | `void`                                                              | The password-set link (R-110); single use by `password_set_at`; `PASSWORD_WEAK` by R-105                                                                                                                       |
| `auth.signOut`           | admin                                                 | `{}`                             | `void`                                                              | Revokes the session; audited `admin.sign_out` on the administrator (T067)                                                                                                                                       |
| `auth.me`                | admin                                                 | `void`                           | `{ adminId, displayName, email }`                                   | The sidebar; a read, audited `auth.read` naming the reader (T067)                                                                                                                                               |

A mutation that takes nothing (`auth.signOut`, `admins.regenerateRecoveryCodes`)
takes the empty object `{}` (`adminEmptyInput` in `@ijazah/contracts/admin`,
strict), never `void`: tRPC 11.19's client sends a mutation whose input is
`undefined` with no body, which its server cannot read (it answers 500) (T099).

## `applications` — the verification queue (FR-160 to FR-162, FR-166)

| Procedure                  | Input                                                                                             | Output                                                                                                                                                                                                                                                                                                   | Audit                                                                                                                                                                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `applications.list`        | `{ tab: 'in_review' \| 'waiting' \| 'decided', search?, page }` (pages of `admin_list_page_size`) | `{ rows: [{ teacherUserId, displayName, email, gender, isMinor, subjects: [{ id, nameAr, nameEn }], callRecordedOn?, submittedAt, status }], total, pageSize }`                                                                                                                                                    | read                                                                                                                                                                                                                                   |
| `applications.get`         | `{ teacherUserId }`                                                                               | `{ …row, qualificationSummary, timezoneCity, accountStatus, identityDocument: { documentId, type, uploadedAt }, credentials: [{ credentialId, subject, status, documentId }], call: { completedOn?, outcome?, notes? }, note?, identityRequest? }`; the decision history is `audit.list({ targetType: 'teacher_application', targetId })` | read                                                                                                                                                                                                                                   |
| `applications.recordCall`  | `{ teacherUserId, completedOn: 'YYYY-MM-DD', timeZone, outcome: 'suitable' \| 'unsuitable', notes }`        | `void`                                                                                                                                                                                                                                                                                                   | `application.record_call`                                                                                                                                                                                                              |
| `applications.approve`     | `{ teacherUserId, note? }`                                                                        | `void`                                                                                                                                                                                                                                                                                                   | `application.approve`; `APPROVAL_BLOCKED` with the reasons (FR-161); sets `verification_status = approved`, `application_status = approved`, `approved_by`/`approved_at`; the approved credentials' subjects become `teacher_subjects` |
| `applications.reject`      | `{ teacherUserId, reasonChoice, note }`                                                           | `void`                                                                                                                                                                                                                                                                                                   | `application.reject`; note mandatory, reaches the applicant                                                                                                                                                                            |
| `applications.requestInfo` | `{ teacherUserId, needed: [choice], note }`                                                       | `void`                                                                                                                                                                                                                                                                                                   | `application.request_info`; `needs_document`                                                                                                                                                                                           |
| `applications.ban`         | `{ teacherUserId, reasonChoice, note }`                                                           | `void`                                                                                                                                                                                                                                                                                                   | `application.ban`; `users.account_status = banned`, every session revoked, no reapply                                                                                                                                                  |

The review's states and answers (T068, batch B13b; owner's decisions at B13's conflict check, 2026-10-22):

- **Tabs and search.** `in_review` is `in_review`, `waiting` is `needs_document`, and `decided` is `rejected`, `banned` or `approved`. Every tab lists the oldest submission first. `search` is the name or the email as typed. `subjects` are those sent with the current application. `isMinor` is computed on read (FR-132).
- **The call.** `callRecordedOn` and `call.completedOn` are calendar days (`verification_call_completed_on date`). `recordCall`'s `timeZone` is used only to refuse a day after today there (`VALIDATION_FAILED` on `completedOn`, code `future`); a zone the time package refuses is `VALIDATION_FAILED` on `timeZone`. A call is recorded on an open application (`in_review` or `needs_document`). `outcome: 'unsuitable'` blocks nothing.
- **`identityRequest?`.** `{ requestId, reason, requestedAt, document?: { documentId, type, submittedAt } }`, the applicant's open identity request. It lets the panel reach `documents.accept` and `documents.requestAnother` from the detail (FR-166).
- **The choices.**
  - `reject`'s `reasonChoice` is `name_mismatch · qualification_gap · call_unsuitable · other`.
  - `requestInfo`'s `needed` is one or more of `id_unclear · ijazah_unreadable · name_mismatch · other`; `ijazah_unreadable` is deprecated, no longer offered by the panel, and stays published until the contract gate can deprecate and then remove a value (T154). Another ijazah is asked for on its credential, `credentials.requestDocument`, which also sets the application waiting on the applicant (T155, owner's decision of 2026-10-29, option (a′)); `ijazah_unreadable` left the list then.
  - `ban`'s `reasonChoice` is `forged_documents · impersonation · call_fraud · other`.
  - These are screens.md's `AdminDecisionDialog` choices.
- **What each decision moves.**
  - `approve` moves an `in_review` application whose call is recorded.
  - `reject` moves `in_review` or `needs_document`.
  - `requestInfo` moves `in_review` only.
  - `ban` moves `in_review`, `needs_document` or `rejected`, through the standing's one ban.
  - Any other state is `CONFLICT` naming the status. An application that is not there is `NOT_FOUND`.
  - `APPROVAL_BLOCKED` carries every reason that holds as `details: [{ path: 'approval', code }]`, the code `call_not_recorded`, `credential_undecided` or `none_approved`.
- **The audit.**
  - Each decision's entry targets `teacher_application` (the applicant's id). Its reason is the note the applicant sees, and its after is the choice (`approve`'s after is the subjects it granted).
  - `recordCall`'s after is `{ completedOn, outcome }`, without the notes.
  - The list and the detail are the read `applications.read`.

## `credentials` — the credential review (FR-163, FR-164)

| Procedure                     | Input                                                                                     | Output                                                                                                                                                                                                                                   | Audit                                                                                                           |
| ----------------------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `credentials.list`            | `{ tab: 'pending' \| 'needs_document' \| 'approved' \| 'rejected', search?, page }`       | `{ rows: [{ credentialId, teacher: { userId, displayName }, subject: { id, nameAr, nameEn }, origin: 'application' \| 'added', submittedAt, status, reviewedAt? }], total, pageSize }`                                                                          | read                                                                                                            |
| `credentials.get`             | `{ credentialId }`                                                                        | `{ credentialId, teacher: { userId, displayName }, subject: { id, nameAr, nameEn }, origin, submittedAt, status, documentId, holderName?, riwaya?, tariq?, chain?: [{ position, names }], reviewReason?, reviewedAt?, reviewedByName? }` | read                                                                                                            |
| `credentials.approve`         | `{ credentialId, holderName, riwaya, tariq?, chain: [{ names: [string, …] }, …], note? }` | `void`                                                                                                                                                                                                                                   | `credential.approve`; writes `isnad_entries` origin first; refuses a second approved credential for the subject |
| `credentials.reject`          | `{ credentialId, reason }`                                                                | `void`                                                                                                                                                                                                                                   | `credential.reject`                                                                                             |
| `credentials.requestDocument` | `{ credentialId, reason }`                                                                | `void`                                                                                                                                                                                                                                   | `credential.request_document`                                                                                   |
| `credentials.correct`         | `{ credentialId, holderName?, riwaya?, tariq?, chain?, reason }`                          | `void`                                                                                                                                                                                                                                   | `credential.correct`; before and after hold the chain (FR-164)                                                  |

The review's states and answers (T069, batch B13a): `approve` and `requestDocument` move a `pending` credential, `reject` a `pending` or `needs_document` one, `correct` an `approved` one, changing only the fields it names (at least one). A refusal is `CONFLICT` with `details: [{ path: 'credentialId', code }]`, the code the credential's state now, or `subject_approved` for a second approved credential for the teacher's subject; a credential that is not there, or a soft-deleted teacher's, is `NOT_FOUND`. An approval makes the subject an approved teacher's at once (FR-153); an applicant's subjects come with `applications.approve`. `requestDocument` on a credential sent with an application in review also sets that application `needs_document`, with the reason as its note and the decision's moment, in the same transaction; one already `needs_document` keeps its note, and an approved teacher's added subject moves no application. Its entry's `before` and `after` are then `{ applicationStatus }`, `in_review` and `needs_document`; it has neither when no application moved (T155). `approve`'s `note` reaches the audit entry's reason, not the teacher; its entry's `after` is the transcription written (`{ holderName, riwaya, tariq, chain: [{ position, names }] }`, `tariq` null when none), and `correct`'s `before` and `after` the same shape. `credentials.list` and `credentials.get` are audited as the read `credentials.read` naming the reader. `search` is the teacher's name as typed; the waiting tabs list the oldest submitted first, the decided ones the latest review first. *(Amended 2026-11-21, SRS DEC-97, T174: the entries of `approve` and `correct` carry `{ riwaya, tariq, chainLength, holderNameChanged }`; the name and the chain before and after are the credential's history. The entries of `approve`, `reject`, `requestDocument` and `correct`, and of an application's decisions, record that a note or reason was given, not its text; each text is held in the history row of that decision or correction (PR #154's review, round 3, N5).)*

## `documents` — the viewer and the verification requests (FR-160, FR-166)

| Procedure                  | Input                  | Output                           | Audit                                                                    |
| -------------------------- | ---------------------- | -------------------------------- | ------------------------------------------------------------------------ |
| `documents.link`           | `{ documentId }`       | `{ url, expiresAt, pageCount? }` | `document.view` (viewing is an action worth a record, NFR-SEC-3)         |
| `users.requireIdentity`    | `{ targetUserId, reason }` | `void`                           | `user.require_identity`; opens the request, sets `verification_required` |
| `documents.accept`         | `{ requestId, note? }` | `void`                           | `verification_request.accept`; closes the request, account `active`      |
| `documents.requestAnother` | `{ requestId, note }`  | `void`                           | `verification_request.request_another`                                   |

The requests' states (T068, batch B13b):

- **`users.requireIdentity`.** It needs an `active` account with no request open; otherwise it is `CONFLICT` on `userId`, the code `request_open` or the account status. The person's field is `targetUserId`, since a field named `userId` is refused in any input (R-GENDER-4).
- **`documents.accept` and `documents.requestAnother`.** Each needs an open request with a document (`CONFLICT` on `requestId`, the code `no_document` or the request's status).
  - `accept` reactivates only an account in `verification_required`. An account suspended meanwhile stays suspended.
  - `requestAnother` closes the request as `replaced`, keeping the document it held, and opens a new request with the note as the reason the person reads. The documents sweep (T093) therefore never removes a document an administrator turned away. The entry's before is `{ documentId }`, the document turned away, and its after `{ requestId }`, the new request (B13b review, owner's decision 2026-10-22).
- **`documents.link`.** It answers no `pageCount` in this phase.

## `teachers` — an approved teacher's standing (FR-165)

| Procedure                 | Input                       | Output | Audit                                                                                                                                                                                                                                           |
| ------------------------- | --------------------------- | ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `teachers.suspend`        | `{ teacherUserId, reason }` | `void` | `teacher.suspend`; `account_status = suspended`, sessions revoked; the enrollment consequences attach through the deletion-and-suspension entry (FR-142)                                                                                        |
| `teachers.revokeApproval` | `{ teacherUserId, reason }` | `void` | `teacher.revoke`; `verification_status = revoked` (the member T011 adds) and `application_status = rejected` with the reason as the note, so the teacher lands on `ApplicationRejected` and returns through `reapply`; the account stays active |
| `teachers.ban`            | `{ teacherUserId, reason }` | `void` | `teacher.ban`                                                                                                                                                                                                                                   |
| `teachers.reinstate`      | `{ teacherUserId, reason }` | `void` | `teacher.reinstate`                                                                                                                                                                                                                             |

The standing's states (T068, batch B13b; data-model.md, ADR 0016 D2):

- **`suspend`.** It moves an approved teacher who is `active` or under an identity request (`verification_required`; B13b review, owner's decision 2026-10-22). It writes `account_status` only.
- **`revokeApproval`.** It moves an approved teacher, active or suspended. It also deletes the teacher's `teacher_subjects` (owner's decision 2026-10-22, FR-153); a new approval grants them again.
- **`ban`.** It moves a teacher approved or whose approval was revoked, and writes `account_status = banned` and `verification_status = banned`. It is the same function as `applications.ban`, which moves an `in_review`, `needs_document` or `rejected` application (B13b review, owner's decision 2026-10-22: a fraud found after a revocation or a rejection is banned at once).
- **`reinstate`.** It moves a suspended teacher back to `active`, or to `verification_required` while an identity request of theirs is `open` (T113, owner's decision 2026-10-28). A ban is not lifted (FR-162).
- **Sessions and consequences.** Each of the three ends every session (`revoked_reason` `account_suspended`, `admin_action`, `account_banned`). Each calls `onAccountTerminated(tx, userId, cause)` (`identity/consequences.ts`, empty in this phase).
- **Refusals.** A refusal is `CONFLICT` on `teacherUserId`, naming the standing. A person with no teacher profile is `NOT_FOUND`.
- **The audit.** Each entry is on the person (`user`), with the reason, the standing it moved from as its `before` and the standing it moved to as its `after` (T116).

## Dialog variants

Every binding action above maps to a row of screens.md §24: the reason is
mandatory where the row says so (the schema's `reason: z.string().min(1)`),
optional where approval's note is optional (`note?`). The admin catalogue's
`admin.dialogs.*` keys are the copy; the audit footer's text is the same for
all.
