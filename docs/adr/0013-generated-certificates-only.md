# ADR 0013 — The MVP grants platform-generated certificates only; the uploaded mode is deferred

**Status:** accepted · **Date:** 2026-10-14 · **Decided by:** the owner, 2026-10-14 · **Amends:** SRS §3.9.2, FR-IJAZAH-2, FR-IJAZAH-13, FR-IJAZAH-14, §6.2 Ijazah entity, §7 Certification, §13, DEC-42, RISK-08 (adds DEC-53); ERD `ijazahs` notes; PLAN.md Phase 4; `docs/design/screens.md` Granting · **Amended by:** ADR 0017 (D1's teacher-side confirm-and-render became request-and-admin-issue; D4's FR-ISNAD-4 reference reads per ADR 0017) · **Amended by:** ADR 0017 (D1's teacher-side confirm-and-render became request-and-admin-issue; D4's FR-ISNAD-4 reference reads per ADR 0017)

## Context

DEC-42 gave the teacher two ways to grant an ijazah (SRS §3.9.2):

- **Mode A, generated.** The platform renders the certificate from its
  template, with the teacher's signature, the chain of transmission
  (FR-ISNAD-7) and a QR code to the public verification page.
- **Mode B, uploaded.** The teacher uploads a scan or a photograph of a paper
  ijazah they issued themselves. The platform shows it but cannot vouch for
  what it says.

Mode B carries costs that Mode A does not:

- **A second upload pipeline.** Certificate files need content sniffing, a
  size limit and the encrypted, signed-URL regime of verification documents
  (FR-IJAZAH-13).
- **A second wording.** The verification page must say, for Mode B only, that
  the platform does not attest the document (FR-IJAZAH-14, R-HONEST-3).
- **An accepted risk.** RISK-08 exists only because of Mode B.
- **A weaker credential.** An uploaded certificate has no chain snapshot,
  since `chain_snapshot` is Mode A only. What it says cannot be checked
  against the admin-verified chain.

Phase 4 has five working days (PLAN.md, the 30-day schedule).

## Decision

### D1 — Every ijazah granted in the MVP is generated by the platform

Granting has no mode choice. The teacher confirms the student, the subject and
the certificate language, and the platform renders the certificate from its
template. FR-IJAZAH-2 is rewritten to say this. FR-IJAZAH-12 still applies:
granting is blocked until the teacher has uploaded a signature image.

### D2 — The uploaded mode is deferred, not deleted

FR-IJAZAH-13 and FR-IJAZAH-14 keep their ids and are marked deferred. They come
back as written if the uploaded mode returns after the MVP. R-HONEST-3 stays in
the constitution unchanged. It applies once an uploaded certificate can exist,
and until then the verification page has one wording.

### D3 — The `mode` column stays and the MVP writes only `generated`

`ijazahs.mode` and the `IjazahMode` enum are already in the Phase 0 schema
(`prisma/schema/certification.prisma`). They stay, so the uploaded mode can
return without a data migration. No MVP code path creates an ijazah whose mode
is `uploaded`, and a Phase 4 test proves the grant service refuses one.

### D4 — The teacher's own qualification documents are not affected

An applicant still uploads the ijazahs and certificates they hold as proof of
qualification for admin review (FR-VERIFY-1, FR-ISNAD-4). Those are
verification documents, not certificates granted on the platform.

## Consequences

- **SRS.** §3.9.2 marks Mode B deferred. FR-IJAZAH-2 is rewritten.
  FR-IJAZAH-13 and FR-IJAZAH-14 are deferred, and RISK-08 is deferred with
  them. DEC-42 is amended and DEC-53 is added. §13 lists teacher-uploaded
  certificates.
- **ERD.** The `ijazahs` notes say that `mode` is always `generated` in the
  MVP, that `chain_snapshot` is always present, and that
  `certificate_storage_key` points to the generated PDF.
- **PLAN.md.** Phase 4 delivers platform-generated granting. Its SRS line
  covers FR-IJAZAH-1…12, and the Mode B upload decision is removed.
- **Mobile.** The Granting screen has no mode choice. It confirms the student,
  subject and language, and shows the certificate preview.
- **Not changed.** The signature upload (FR-IJAZAH-12), the paper-copy flag
  (FR-IJAZAH-5), revocation, barring and the public verification page.
